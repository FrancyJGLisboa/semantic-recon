What an agent

A system for turning an unfamiliar API, database, MCP server, or codebase into a contract that changes how every agent afterward behaves.

A contract is not successful because it is complete. It is successful because it changes the behavior of the agent that consults it. Everything below follows from taking that seriously — and from noticing that most documentation fails not by being wrong, but by not being read at the moment it mattered.

The gap

Knowing is not doing

An agent under context pressure reads one file and starts working. Every rule that lives only in the other eleven files is, functionally, a rule that does not exist.

So the design question is not what should the contract contain. It is: along the path an agent actually walks, where can a wrong answer still escape — and what stands in its way?

The pipeline

The exam is written before the studying

Eleven phases run in order, each behind a gate. One of them is sealed off from the rest, and that seal is the load-bearing structural decision in the whole system.

If the final auditor writes its own questions after discovery, it will write questions the contract happens to answer. The audit becomes theater. So the questions are frozen first, by an agent that knows almost nothing, and handed directly to the auditor — over the heads of every phase in between.

Triage

Confidence is the wrong axis

Every claim gets two labels. How well it is supported — and what happens when it is violated. Sorting work by the first is the intuitive move and the wrong one.

A rule that fails loudly is already half-safe: the system raises, someone investigates. The dangerous object is the claim you are confident about that returns a plausible number when it is wrong. Nobody investigates a plausible number.

That rule is why the leftmost column carries the accent colour: it is the only column where documenting the finding is never a sufficient response.

Portability

One pack, four kinds of system

The phases never change. What changes is what their vocabulary is bound to — and binding it explicitly, before discovery starts, is what keeps a database run from inheriting an API run's assumptions.

The Target Profiler writes this binding into the contract before any other phase runs. Later phases read the binding, not the generic table.

The gate

Eight ways to be told no

Each raises rather than warns, and each message carries three things: what was refused, why in one sentence, and the correct call ready to copy. An override is possible only through an explicit named argument, never a silent default.

  1. UnresolvedContractRuleThe request depends on a question only a human can answer. The refusal quotes that question and names its owner.
  2. ForbiddenJoinA join documented as invalid, refused with the fan-out factor that was measured when it was tested.
  3. IncompatibleCombinationSources, vintages, versions, units, or grains mixed without an explicit override.
  4. AmbiguousTemporalSemantics“Latest” with no time axis named. Published, observed, revised, and ingested routinely disagree.
  5. InvalidAggregationA measure summed along an axis it is not additive over.
  6. KnownTrapA shape already documented in the traps file, refused with the wrong value shown beside the right one.
  7. LimitExceededPast a hard limit that was observed rather than assumed.
  8. ForeignContractDataData stamped with another contract's id. The cross-system guard: system A's values reaching system B's functions fail loudly instead of blending in.
Where a rule should live

Push everything downward

Three layers hold the knowledge, and they are not equally reliable. The governing move is to migrate each rule as far down as it can go — because only the bottom layer holds when nobody is paying attention.
