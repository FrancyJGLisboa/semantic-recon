semantic-recon · walkthrough

Your first
contract

Better conditions for building AI agents with expertise on a system. Install to working code, with output from a real run against a public API you can reproduce yourself.

AI assistants can use real systems now. The risk is not that they crash.

It is that they hand you a number that is wrong and looks completely fine. Here is a real one, from a public weather service anyone can call.

“How much rain fell in Tokyo yesterday?”

4.1 mmone setting
1.2 mmanother setting

Same question, same day, same service. No error either way — both come back looking like the answer. And the setting is one most people never touch.

Now the part that makes it dangerous. If you check whether that setting matters by looking at temperature instead of rain, temperature comes back identical both ways. So you conclude the setting is cosmetic — and from that moment you are confidently wrong about rain.

Nobody hid this. It is the kind of thing that is obvious to whoever built the service and invisible to everyone else. Every real system has a handful of them.

It is the difference between a new hire and a senior colleague. The senior does not know more facts. They know where the landmines are, and they stop you before you step on one. This tool writes that down — and makes it stop you by itself.

So: it sends an AI to poke at a system for an hour. Try things, break things, write down what surprised it, with the actual numbers. Then it turns every surprise into a tripwire in code. After that, any AI working with that system hits the tripwire instead of the wrong answer — without having read anything.

We tested that the obvious way. We built a small weather app with zero safety checks written into it. The tool's output stopped it five times. Two rounds of following the error messages and it was correct — including for a reason its author never knew.

That is what has been tried so far: two public weather services, one small app. The rest of this page is how you do it yourself.

What changes

Same question, same code, same API. The difference is whether a contract exists.

Without

>>> forecast(52.52, 13.41)
2026-09-01: 22.2 °C

Which of five models answered? Unknown. Which grid cell — you asked for one and got another a kilometre away? Unknown. Comparable to the figure you stored yesterday? No way to tell. Nothing is wrong on the screen.

With

>>> forecast(52.52, 13.41)
REFUSED: a forecast request with no explicit model
INSTEAD: pass models='icon_seamless' …

2026-09-01: 22.2 °C
— forecast · icon_seamless · grid 52.5200,13.4200
  (38 m) · tz Europe/Berlin

Stopped before the ambiguous call, told exactly how to fix it, and the answer arrives naming what produced it. You did not have to know any of that.

That is the whole trade. You spend an hour once. After that, correctness on this system stops depending on whether the next person happens to know the five things that matter.

01

Install

$ git clone https://github.com/FrancyJGLisboa/semantic-recon.git
$ cd semantic-recon && ./scripts/install.sh

Claude Code    linked  -> ~/.claude/skills/semantic-recon
Codex CLI      linked  -> ~/.codex/skills/semantic-recon
Copilot CLI    linked  -> ~/.copilot/skills/semantic-recon
registry       created -> ~/contracts/INDEX.md

All three CLIs read the same <config>/skills/<name>/SKILL.md layout, so one source installs to whichever you have. It symlinks — git pull updates every one of them at once.

In Claude Code, type / and look for semantic-recon; it appears without restarting. Loading has only been confirmed in Claude Code — check yours before relying on it.

02

The prompt

/semantic-recon

TARGET_TYPE:            DATA_API
TARGET_LOCATION:        https://api.open-meteo.com
BLAST_RADIUS_OF_MISUSE: Test run, no production consumer.
OUT_OF_SCOPE:           Everything except Forecast and Historical Archive.
CALL_BUDGET:            120

Two fields are yours. Everything else is determined for you — including the contract's name. You never pick a slug.

FieldWhy it has to be you
BLAST_RADIUS_
OF_MISUSE		Only you know what breaks in your business if an agent gets this system wrong.
OUT_OF_SCOPEOnly you know where this run should stop.

TARGET_TYPE is one of DATA_API, DATABASE, MCP_SERVER, CODEBASE. With credentials, add the variable name — never the value:

CREDENTIALS_AVAILABLE:  yes, via $MYSYSTEM_TOKEN
WRITE_ACCESS:           read-only
03

It stops after phase 1, on purpose

The first phase costs at most three operations and hands back a proposed name with the derivation that produced it. Confirm before it spends the call budget.

contract_id_derivation:
  raw_name:            "Open-Meteo.com"
  source:              <title> of https://open-meteo.com/en/docs
  normalized_to:       open_meteo
  collision_checked:   yes — against ~/contracts/INDEX.md
  escalated_to_human:  no

The slug is derived deterministically: the same asserted name always normalizes to the same result. Two runs can still read that name from different surfaces — a page title one time, an OpenAPI info.title the next — so the collision check against the registry catches the rest. After you say continue the name is frozen, and it appears in the folder, the Python package, and every file header.

What comes out

├── tests/                 every trap is a regression test
└── evidence/              frozen questions, observations, counterexamples, audit

Reconstructible

  • ENTITIES · METRICS
  • ACCESS · DIMENSIONS
  • SOURCES

A competent agent could rebuild most of this from the vendor's docs. Useful, saves time, not rare.

The point

  • TRAPS · UNCERTAINTIES
  • AUTHORITY_POLICY
  • counterexamples · validators

None of it exists without having probed the system. This is the half nobody can reconstruct at any effort.

Open-Meteo does document some of this in prose. That is not the same as an agent loading it at the moment it builds a request, which is the entire point: the contract turns each one into a refusal that fires whether or not anybody read anything. Five, from the real run, each carrying the measurement that established it:

Two products, one dateArchive says 23.4 °C, forecast says 24.2 °C — different grid cells, different models, both HTTP 200.
timezone changes valuesTokyo rainfall: 4.1 mm in UTC, 1.2 mm in Asia/Tokyo. Temperature is identical either way, so a temperature spot-check "proves" it does not matter.
A typo returns 200Unknown parameters are silently ignored, so a misspelled timezone quietly applies the default.
The archive is not all ERA5ERA5 stops ~5 days short; the default fills the gap from an unnamed source with no seam marker.
best_match is a choiceA per-location selection, never reported, 1.7 °C of spread between models.
05

Reading the verdict

PASSClean-room agent answered the frozen questions correctly, nothing unresolved.
PASS_WITH_
UNRESOLVED_ITEMS		Correct, but some questions need a human or the vendor.
FAILDo not use it yet. The report says why.
The middle one is normal, and is not a defect. It means the contract will be correct but conservative — it refuses where a fully-resolved contract would answer. Each unresolved item carries a precise question and an owner. Answering them and refreshing is how a contract gets less conservative over time.
06

Three ways to use what came out

Ranked by how little you have to do. The first needs no code at all.

  1. Paste the bootstrap into any agentno code

    Ten lines from references/downstream.md. The agent reads the routing table, calls the contract's functions instead of the API, and reports refusals instead of guessing. Works in any assistant that can read a folder.

  2. Import the code into what you are buildingone import

    The refusals stop being advice and become structural — they fire whether or not anyone read the documentation.

  3. Point another agent at the folder and let it buildthe leverage

    This is where it compounds. Build five things on one contract and all five inherit the same traps, without any of their authors learning them.

from data_contract_open_meteo.code import client, series

res = client.query({"product": "forecast", "latitude": 52.52, "longitude": 13.41,
                    "daily": "temperature_2m_max", "timezone": "UTC",
                    "models": "icon_seamless", "forecast_days": 3})

print(series.format_with_provenance(res[0]["daily"]["temperature_2m_max"]))

Leave out models and it stops you:

REFUSED: a forecast request with no explicit model
WHY: best_match selects a model per location, never reports which, and the spread across models reached 1.7 C at a 3-day horizon (U-02, CE-06)
INSTEAD: pass models='icon_seamless' (or ecmwf_ifs025 / gfs_seamless), or pass allow_best_match=True for a single casual lookup you will label

Every refusal carries three things: what was refused, why in one sentence, and the correct call ready to copy.

The third way, measured. We wrote a weather skill with zero refusal logic of its own — no checks, no validation, nothing about models or timezones. Its contract stopped it five times. Two rounds of following the messages and it was correct, including for a reason its author never knew: two models resolve to different grid cells.

Anything a person will read goes through format_with_provenance(). It is the only formatter the contract ships, and it cannot omit the source.

07

A second system

Run the skill again; the profiler checks for collisions itself. Once two contracts can answer the same question, an arbiter appears above them. Ask it rather than choosing.

authority.route({"date": date(2019, 3, 15)})
<Ruling open_meteo by CAPABILITY: the only registered contract that can
 answer: met_locationforecast does not serve dates before today>

authority.route({"date": date(2026, 9, 3)}, country="NO")
REFUSED: choosing between met_locationforecast, open_meteo
WHY: all of them can answer this, so capability does not decide, and no
     operator preference is declared ...
A guessed preference is indistinguishable from a policy. It gets inherited, cited, and defended by agents that have no idea a human never made it.

So capability decides where capability can, and the rest comes back to you. Comparing two contracts is allowed. Merging them is not, and takes no override.

08

Keeping it true

>>> contract_health.report()
CONTRACT open_meteo — verified 2026-09-01 (0 days ago) — FRESH
smoke test: PASS

When it goes stale or reports drift, run /semantic-recon refresh open_meteo. A refresh reads .contract_id and never re-derives the slug — that would fork the contract. It re-runs only the flagged phases, re-answers the same frozen questions, and produces a semantic diff before anything is overwritten.

—

When not to use this

The return comes from repetition. Not for a one-off query. The cost is paid once and the protection is distributed forever, so the return comes from repetition: build five things on one contract and all five inherit the same traps and refusals without anyone rediscovering them. For a single question, just call the API.

What has and has not been shown

Established

  • Two contracts, audited clean-room against questions frozen before discovery: 20/22 and 17/17 correct, zero wrong
  • Ten falsified assumptions, each keeping its measured counterexample
  • One skill inherited five refusals it never wrote
  • 64 tests · loading confirmed in Claude Code

Not established

  • Loading in Codex or Copilot CLI — the layout matches, nobody has invoked it there
  • Any target that is not a DATA_API; the other three vocabularies are written and unexercised
  • Anything general about agent behaviour

A project about evidence has to meet its own standard. These boundaries are in the README too.
